# ADR-0002: ใช้เหตุการณ์สำหรับงานหลังการสั่งซื้อ

- **Status:** Proposed
- **Date:** 2026-10-25
- **Deciders:** ยังไม่ระบุ

## Context and problem

- หลักฐาน: requirement ในข้อความผู้ใช้สำหรับ run: a, context: none ไม่ใช่ไฟล์ใน repository
- หลังสั่งซื้อ ต้องส่งอีเมลยืนยันผ่าน MailFast แทน mock emailservice logic ให้คะแนนผ่าน loyaltyservice ที่จะสร้าง และบันทึกเหตุการณ์สำหรับทีมการตลาด
- ทีมการตลาดคาดว่าจะเพิ่ม SMS, fraud scoring และการปรับปรุง recommendations ในปีหน้า จึงต้องเลือกวิธีประสานงานที่รองรับงานเพิ่ม
- ไม่ได้อ่านโค้ดระบบตามข้อจำกัด context: none ข้อมูลเกี่ยวกับ dependency, protocol, ฐานข้อมูล และขอบเขต transaction เดิม: Not evidenced in the provided files
- **[Assumption]** งานหลังสั่งซื้อยอมให้เสร็จภายหลังการตอบว่าสั่งซื้อสำเร็จได้ โดยยังต้องดำเนินการให้ครบ ต้องยืนยันก่อนยอมรับ ADR

## Decision drivers

ลำดับต่อไปนี้เป็นข้อเสนอ ยังไม่ได้รับการยืนยันจากผู้เกี่ยวข้อง

1. เพิ่มงานใหม่โดยลดการแก้กระบวนการสั่งซื้อ — modifiability
2. รักษางานที่ยังไม่เสร็จและกู้คืนเมื่อปลายทางขัดข้อง — reliability
3. ลดผลกระทบจากปลายทางล่มต่อการสั่งซื้อ — availability
4. ตรวจสอบสถานะและป้องกันผลข้างเคียงซ้ำ — observability และ correctness
5. ควบคุมภาระ infrastructure และการดูแล — cost และ operability

## Considered options

1. เรียก MailFast, loyaltyservice และปลายทาง analytics โดยตรงแบบ synchronous จากกระบวนการสั่งซื้อ
2. ส่งงานให้ตัวประสานงานเบื้องหลังแบบ durable ซึ่งเรียกปลายทางและติดตามสถานะงาน
3. เผยแพร่เหตุการณ์ผ่าน message broker แบบ durable โดยแยกผู้รับงานแต่ละประเภท

### Pros and cons of the options

| Option | Pros | Cons |
|---|---|---|
| 1 — เรียกโดยตรง | ลำดับควบคุมตรงไปตรงมา; ทราบผลแต่ละการเรียกทันที; ไม่ต้องเพิ่ม broker | เวลาตอบและความพร้อมใช้งานผูกกับปลายทาง; การเรียกหลายปลายทางไม่ใช่ transaction เดียวกันโดยอัตโนมัติ; เพิ่มงานต้องแก้ผู้เรียก |
| 2 — ตัวประสานงานเบื้องหลัง | แยกเวลาตอบการสั่งซื้อจากปลายทาง; รวมสถานะและ retry; ควบคุมลำดับงานได้ชัดเจน | ต้องสร้างและดูแลสถานะ workflow; เพิ่มงานต้องแก้ตัวประสานงาน; ต้องจัดการคอขวดและการกู้คืนของตัวประสานงาน |
| 3 — เหตุการณ์และ broker | เพิ่มผู้รับงานแยกกันได้; แยก retry และการขยายกำลัง; ลดการผูกความพร้อมใช้งานกับปลายทาง | เพิ่ม infrastructure; ผลสำเร็จเกิดต่างเวลากัน; ต้องจัดการเหตุการณ์ซ้ำ schema และการติดตามข้ามองค์ประกอบ |

## Decision

เสนอเลือกตัวเลือก 3 เพราะ requirement ระบุว่าจะมีงานหลังสั่งซื้อเพิ่ม รายละเอียดต่อไปนี้เป็นการออกแบบที่เสนอ ไม่ใช่ข้อเท็จจริงที่กู้คืนจากโค้ด

- ให้ส่วนที่ยืนยันคำสั่งซื้อสร้างเหตุการณ์ OrderPlaced เมื่อบันทึกคำสั่งซื้อสำเร็จ มี event_id, order_id และรุ่น schema พร้อมข้อมูลขั้นต่ำสำหรับผู้รับงาน ไม่ใส่ข้อมูลชำระเงินที่ไม่จำเป็น
- บันทึกคำสั่งซื้อและเจตนาส่งเหตุการณ์แบบ atomic เช่น transactional outbox หากแหล่งเก็บคำสั่งซื้อรองรับ transaction ร่วมกัน แล้วให้ตัวส่งเผยแพร่จาก outbox ไปยัง broker หากทำไม่ได้ ต้องเลือกและพิสูจน์กลไกป้องกันเหตุการณ์สูญหายก่อนยอมรับ ADR ขณะนี้ยังไม่ทราบแหล่งเก็บคำสั่งซื้อหรือความสามารถดังกล่าว
- ใช้ broker แบบ durable ที่รองรับ acknowledgement และ at-least-once delivery มี subscription หรือคิวแยกสำหรับอีเมล คะแนนสะสม และ analytics เพื่อให้ทุกงานได้รับเหตุการณ์ ไม่ให้ผู้รับทั้งสามแย่งข้อความจากคิวเดียวกัน
- เสนอปรับ emailservice เป็นผู้รับเหตุการณ์และเรียก MailFast แทน mock logic ให้ loyaltyservice รับเหตุการณ์เพื่อให้คะแนน และให้ผู้รับงาน analytics บันทึกเหตุการณ์สำหรับทีมการตลาด จุดจัดเก็บ analytics ยังต้องเลือก
- ผู้รับงานยืนยันรับข้อความหลังบันทึกผลสำเร็จ ใช้ retry แบบมี backoff พร้อมที่พักข้อความล้มเหลวและกระบวนการนำกลับมาทำใหม่ ต้องกำหนดจำนวน retry และอายุเก็บข้อมูลภายหลัง
- ตรวจซ้ำด้วย event_id และใช้ order_id ร่วมกับประเภทการให้คะแนนเพื่อป้องกันคะแนนซ้ำ ผูกการบันทึกว่าประมวลผลแล้วกับผลลัพธ์ใน transaction เดียวกันเมื่อทำได้
- สำหรับอีเมล ใช้ idempotency key หาก MailFast รองรับ หาก timeout หลังผู้ให้บริการรับงานแล้ว ต้องตรวจสอบหรือกระทบยอดก่อนส่งซ้ำ ไม่อ้างว่าส่งอีเมลได้ exactly-once
- เพิ่ม SMS และการปรับปรุง recommendations เป็นผู้รับเหตุการณ์ใหม่ได้เมื่อยืนยันสัญญาข้อมูล ส่วน fraud scoring ต้องยืนยันว่าทำภายหลังได้หรือใช้อนุมัติคำสั่งซื้อ หากต้องใช้อนุมัติ ต้องออกแบบจุดตัดสินใจก่อนยืนยันคำสั่งซื้อเพิ่มเติม
- ยังไม่เลือกผลิตภัณฑ์ broker หรือ protocol เพราะไม่มีข้อมูลข้อจำกัด ทีม ทรัพยากร และปริมาณงาน

## Consequences

- **Positive:** เพิ่มผู้รับงานใหม่โดยลดการแก้กระบวนการสั่งซื้อ หากข้อมูลเหตุการณ์เพียงพอ — คุณลักษณะคุณภาพ: modifiability
- **Positive:** ผู้รับงานแต่ละประเภทหยุดและกลับมาประมวลผลต่อได้โดยไม่ต้องรอทุกปลายทางพร้อมกัน — คุณลักษณะคุณภาพ: availability และ reliability
- **Positive:** ตัดเวลารอผลปลายทางออกจากเส้นทางตอบการสั่งซื้อ โดยยังมีต้นทุนบันทึกเหตุการณ์แบบ durable — คุณลักษณะคุณภาพ: performance
- **Negative:** อีเมล คะแนน และ analytics อาจเสร็จต่างเวลา ต้องสื่อสารสถานะที่เหมาะสม — คุณลักษณะคุณภาพ: consistency และ usability
- **Negative:** ต้องดูแล broker, outbox, retry, schema และเครื่องมือติดตามเพิ่ม — คุณลักษณะคุณภาพ: cost และ operability
- **Risks and mitigations:** เหตุการณ์อาจหายระหว่างบันทึกคำสั่งซื้อกับส่งเข้า broker; ใช้การบันทึกเจตนาส่งแบบ atomic และทดสอบจุดล้มเหลว — คุณลักษณะคุณภาพ: reliability
- **Risks and mitigations:** ส่งซ้ำอาจให้คะแนนหรือส่งอีเมลซ้ำ; ตรวจซ้ำโดยผูกกับผลลัพธ์ และกระทบยอดผลภายนอกที่ไม่ชัดเจน — คุณลักษณะคุณภาพ: correctness
- **Risks and mitigations:** งานค้างหรือข้อความผิดรูปทำให้ข้อมูลการตลาดไม่ครบ; แยกคิว แจ้งเตือน backlog และตรวจข้อความก่อน replay — คุณลักษณะคุณภาพ: observability และ reliability
- **Risks and mitigations:** ข้อมูลลูกค้าในเหตุการณ์เพิ่มพื้นที่เปิดเผยข้อมูล; จำกัด payload สิทธิ์เข้าถึง และอายุเก็บข้อมูล — คุณลักษณะคุณภาพ: security และ privacy

## Validation

- ทดสอบคำสั่งซื้อสำเร็จแล้วตรวจว่า MailFast รับงานอีเมล loyaltyservice บันทึกคะแนน และปลายทาง analytics บันทึกเหตุการณ์ โดยเชื่อมโยงด้วย order_id
- จำลองความล้มเหลวก่อนและหลัง commit คำสั่งซื้อ หลังเผยแพร่เหตุการณ์ และก่อน acknowledgement ตรวจว่าไม่มีเหตุการณ์จากคำสั่งซื้อที่ไม่สำเร็จ และงานของคำสั่งซื้อที่สำเร็จกลับมาดำเนินการได้
- ส่งเหตุการณ์ซ้ำและ restart ผู้รับงาน ตรวจว่าคะแนนและรายการ analytics ไม่ซ้ำตามกติกาที่ตกลง ทดสอบกรณี MailFast รับงานแล้วแต่การตอบกลับหายด้วย
- ปิด MailFast และผู้รับงานแต่ละตัวชั่วคราว ตรวจการคงอยู่ของงาน การแยกผลกระทบ และการระบาย backlog เมื่อกลับมา
- ติดตามเวลาตั้งแต่สั่งซื้อถึงแต่ละงานเสร็จ จำนวน retry งานล้มเหลว เหตุการณ์ซ้ำ และอายุงานค้าง ทดสอบภาระงานหลังตกลงปริมาณงานและเกณฑ์ยอมรับ ไม่ถือว่าผ่านขณะยังไม่มีเกณฑ์
- ทบทวน ADR เมื่อทราบความสามารถ MailFast ขอบเขต transaction และข้อกำหนด fraud scoring

- จุดใดถือว่าสั่งซื้อสำเร็จ ใช้แหล่งเก็บข้อมูลใด และรองรับการบันทึกคำสั่งซื้อกับ outbox แบบ atomic หรือไม่?
- อีเมล คะแนน และ analytics ต้องเสร็จภายในเวลาเท่าใด? ยอมรับการเสร็จภายหลังได้หรือไม่?
- ปริมาณคำสั่งซื้อ อัตราสูงสุด เป้าหมาย availability และระยะเวลารองรับปลายทางล่มเป็นเท่าใด?
- MailFast มี API, protocol, rate limit, idempotency key และวิธีตรวจสถานะอย่างไร? ต้องติดตามการรับคำขอและการส่งถึงผู้รับอย่างไร?
- คะแนนคำนวณอย่างไร และต้องคืนคะแนนเมื่อยกเลิกหรือคืนสินค้าอย่างไร?
- analytics ต้องการ schema ใด เก็บที่ใด และมีกติกาจัดการเหตุการณ์ซ้ำหรือลำดับสลับอย่างไร?
- fraud scoring ต้องเสร็จก่อนยืนยันคำสั่งซื้อหรือทำภายหลังได้?
- ทีมมีทักษะ งบประมาณ และ infrastructure ใดสำหรับ broker? ใครรับผิดชอบการแจ้งเตือน กระทบยอด และ replay?
- นโยบาย retry, retention, สิทธิ์เข้าถึง และการจัดการข้อมูลส่วนบุคคลเป็นอย่างไร?
