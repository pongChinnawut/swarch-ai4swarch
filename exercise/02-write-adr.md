# งานที่ 2: เขียน ADR สำหรับความต้องการใหม่ (ประมาณ 20 นาที)

> **เชื่อมโยงกับการบรรยาย:** T3 (GPT-4 แบบ zero-shot ให้ผลที่สอดคล้องกัน แต่ *ครบถ้วนน้อยกว่ามนุษย์* ส่วน few-shot ช่วยลดช่องว่างได้มาก), AICH3 (บริบท), สัปดาห์ที่ 10 (message broker)
> **คำถาม:** ADR ที่ AI เขียนดีขึ้นแค่ไหน เมื่อให้ตัวอย่างและบริบทจริงแก่ AI

อ่าน [สถานการณ์ (ภาษาไทย)](../docs/scenario.th.md) ก่อน: ความต้องการ **R-12** ว่าด้วยสิ่งที่เกิดขึ้นหลังจากลูกค้าสั่งซื้อสินค้า

ในแต่ละ run ให้เริ่ม **แชตหรือ session ใหม่** แล้วส่งข้อความด้านล่าง โดยแทนที่ `<paste R-12 here>` ด้วยข้อความ R-12 ภาษาอังกฤษที่อยู่ในกรอบอ้างอิงของ scenario

**Run a: ไม่มีตัวอย่าง (zero-shot)** → [`outputs/2a-adr.md`](outputs/2a-adr.md)
```
Follow prompts/2-write-adr.md
run: a
context: none
requirement: <paste R-12 here>
language: Thai
```

**Run b: มีตัวอย่าง + บริบท** → [`outputs/2b-adr.md`](outputs/2b-adr.md)
```
Follow prompts/2-write-adr.md
run: b
context: docs/scenario.md, docs/adr/0001-use-redis-for-cart-storage.md, system/online-boutique/src/checkoutservice/main.go
requirement: <paste R-12 here>
language: Thai
```

> บรรทัด `language: Thai` ทำให้ agent เขียน ADR เป็นภาษาไทย (หัวข้อของ template และชื่อทางเทคนิคยังคงเป็นภาษาอังกฤษ) หากต้องการภาษาอังกฤษให้ลบบรรทัดนี้ **ใช้ภาษาเดียวกันทั้ง Run a และ Run b** เพื่อให้เปรียบเทียบกันได้

> ใน Run a ให้ตรวจว่า agent ไม่ได้อ่านไฟล์อื่นนอกจาก template จริง ๆ หาก agent เปิด `docs/scenario.md` ให้บันทึกไว้ใน prompt log เพราะจะทำให้การเปรียบเทียบเปลี่ยนไป

## เปรียบเทียบ a กับ b

> AI ช่วยเติมจาก `exercise/outputs/2a-adr.md`, `exercise/outputs/2b-adr.md` และตรวจตัวเลขกับ `docs/scenario.md` โดยไม่ได้รัน a/b ใหม่ การอ่านเฉพาะผลลัพธ์ไม่สามารถยืนยันประวัติการเปิดไฟล์ของแต่ละ run ได้ ต้องตรวจ session/prompt log เพิ่ม

| เกณฑ์ | Run a | Run b |
|---|---|---|
| ใช้ตัวเลขจาก scenario หรือไม่ (latency, ช่วงพีก, ข้อจำกัดของ MailFast) | ไม่ระบุตัวเลข latency โหลด หรือโควตา เพราะได้รับเฉพาะ R-12; เก็บเป็น Open questions และยังไม่เลือกผลิตภัณฑ์ broker | ระบุ checkout p95 ≤ 500 ms จากเดิมประมาณ 300 ms, พีก 200 orders/s และ MailFast p95 1.5 s / p99 8 s, ผิดพลาด 0.5%, จำกัด 50 emails/s ตรงกับ `docs/scenario.md:24–26` |
| ทางเลือกที่พิจารณา (ระบุ) | 1) เรียกปลายทางโดยตรงแบบ synchronous 2) ตัวประสานงานเบื้องหลังที่มีสถานะงานถาวร 3) เหตุการณ์ผ่าน durable message broker; เสนอเลือกข้อ 3 โดยยังไม่เลือกผลิตภัณฑ์ | 1) เรียก synchronous พร้อม timeout/จัดการข้อผิดพลาด 2) บันทึกงานถาวรและให้ตัวประสานงานเรียกผ่าน gRPC 3) บันทึก order/outbox แบบ atomic แล้วส่งผ่าน RabbitMQ แยกคิว; เสนอเลือกข้อ 3 โดยอ้างทักษะทีมและข้อจำกัดใน `docs/scenario.md:29–30` |
| จัดการแต้มสะสมแบบ "ครั้งเดียวเท่านั้น" และ rate limit ของ MailFast หรือไม่ อย่างไร | เสนอ deduplication ด้วย event_id และ order_id ร่วมกับชนิดการให้แต้ม โดยผูกหลักฐานประมวลผลกับผลลัพธ์ใน transaction เดียวกันเมื่อทำได้ แต่ไม่มีเป้า 1 นาที; rate limit ของ MailFast ยังเป็นคำถาม ไม่กำหนดอัตรา | กำหนด ledger กับหลักฐานประมวลผลใน transaction เดียว พร้อม unique key ของ order_id/ชนิดแต้ม และ ack หลัง commit; ทดสอบครั้งเดียวภายใน 60 วินาที จำกัดอีเมลรวมทุก replica และ retry ≤ 50/s พร้อม backoff/คิวแยก และประเมิน backlog อย่างน้อย 150 ฉบับ/s เมื่อหนึ่งอีเมลต่อ order |
| มีสิ่งที่แต่งขึ้นเองหรือไม่ (ตัวเลข เครื่องมือ หรือข้อเท็จจริงที่ไม่มีใน scenario) | ไม่พบการสร้างตัวเลขแล้วอ้างเป็นข้อเท็จจริง; outbox, event_id, broker และ deduplication เป็นการออกแบบที่เสนอ ส่วนการยอมให้งานเสร็จหลังตอบ checkout ติดป้าย [Assumption] และยังต้องยืนยัน | ไม่พบตัวเลขขัดกับ scenario; ค่า backlog 150 ฉบับ/s เป็น [Inferred] ภายใต้สมมติฐานหนึ่งอีเมลต่อ order ส่วน AMQP, quorum queue, publisher confirms, outbox และ ledger เป็นข้อเสนอใหม่ ไม่ใช่องค์ประกอบที่ scenario ยืนยันว่ามีอยู่แล้ว; ควรแก้ถ้อยคำ “บริษัทต้องการ” เป็น “บริษัทมีความต้องการใช้เป็นลำดับแรก” เพราะ `docs/scenario.md:30` ใช้คำว่า prefers |

## รับผิดชอบ ADR ฉบับสุดท้ายของตัวเอง

นิสิตคือสถาปนิก ให้คัดลอก `outputs/2b-adr.md` ไปที่ `docs/adr/0002-<short-title>.md` แล้วแก้ไข**ด้วยตัวเอง**จนพร้อมจะลงชื่อรับรอง ห้ามให้ agent ทำส่วนนี้

- แก้ไขสิ่งที่ผิดหรือแต่งขึ้นเอง และเพิ่มสิ่งที่ขาดหายไป
- ตัดสินใจขั้นสุดท้ายด้วยตัวเอง นิสิตสามารถไม่เห็นด้วยกับ AI ได้

นิสิตจะต้องปกป้อง ADR นี้ต่อหน้าคณะกรรมการรีวิวในส่วน B จึงต้องอธิบายทุกการตัดสินใจใน ADR ได้

| # | สิ่งที่เปลี่ยนจากร่างของ AI | เหตุผล |
|---|---|---|
| 1 | ระบุชื่อผู้รับผิดชอบ วันที่ปรับปรุง และสถานะ Proposed ที่มีเงื่อนไข พร้อมระบุว่า AI ช่วยปรับฉบับส่ง | ให้มีเจ้าของการตัดสินใจและไม่อ้างว่าการส่งเอกสารเท่ากับผ่านการทดสอบหรืออนุมัติเปิดใช้ |
| 2 | เลือก PostgreSQL เป็นข้อเสนอใหม่สำหรับ order/outbox และ ledger; เพิ่ม request idempotency, สถานะคำสั่งซื้อ, reconciliation และพฤติกรรมเมื่อเขียนไม่ได้ | ลดช่องว่างระหว่าง payment/shipping กับการบันทึก และป้องกันการลองคำขอเดิมซ้ำโดยไม่ตรวจผล |
| 3 | กำหนด confirmed_at เป็นจุดเริ่ม deadline แต้ม เพิ่มเงื่อนไขความจุอีเมล เกณฑ์เปิดใช้/ย้อนกลับ และขอบเขต fraud scoring | ทำให้ตรวจรับตามข้อกำหนดได้โดยไม่ผ่อน SLA หรือสร้างตัวเลขธุรกิจที่ยังไม่มีหลักฐาน |
