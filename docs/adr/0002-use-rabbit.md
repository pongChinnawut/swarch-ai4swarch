# ADR-0002: ใช้ RabbitMQ แยกงานหลังสั่งซื้อออกจาก checkout

- **Status:** Proposed
- **Date:** 2026-10-29
- **Deciders:** ชินนวุฒิ แก้วฉิม — ผู้รับผิดชอบการตัดสินใจในแบบฝึกหัด; การเปิดใช้จริงต้องผ่านเงื่อนไขใน Validation

## Context and problem

- R-12 กำหนดให้ส่งอีเมลผ่าน MailFast แทน mock logic ของ emailservice เพิ่ม loyaltyservice และบันทึกเหตุการณ์เพื่อการตลาด รวมถึงรองรับ SMS, fraud scoring และการปรับ recommendations ในปีถัดไป (docs/scenario.md:7–14 และข้อกำหนดจากผู้ใช้)
- ปัจจุบัน PlaceOrder เรียกชำระเงิน ส่งสินค้า ล้างตะกร้า สร้าง OrderResult แล้วรอ sendOrderConfirmation ก่อนตอบกลับ หากส่งอีเมลผิดพลาดจะบันทึกคำเตือนและยังตอบสำเร็จ การเรียกอีเมลใช้ gRPC (system/online-boutique/src/checkoutservice/main.go:252–279, sendOrderConfirmation:379–383)
- checkout ต้องมี p95 ≤ 500 ms จากปัจจุบันประมาณ 300 ms รองรับพีก 200 orders/s ส่วน MailFast มี p95 1.5 s, p99 8 s ล้มเหลวประมาณ 0.5% และจำกัด 50 emails/s จึงมีความเสี่ยงต่อ latency หากยังรออีเมลในเส้นทางตอบกลับ ไม่ควรนำค่า percentile มาบวกเพื่ออ้างว่าเป็น p95 รวมโดยตรง (docs/scenario.md:24–26; ข้อประเมินความเสี่ยงนี้เป็น **[Inferred]**)
- แต้มต้องเข้าภายใน 1 นาทีและห้ามซ้ำ คำสั่งซื้อต้องไม่ล้มเหลวเพราะอีเมล loyalty หรือ analytics ใช้งานไม่ได้ ทีมมี 4 คน ถนัด Go/gRPC และ 2 คนเคยใช้ RabbitMQ ระบบอยู่บน Kubernetes และบริษัทให้ความสำคัญกับ open-source ที่ self-hosted เป็นลำดับแรก (docs/scenario.md:27–30)
- การบันทึกคำสั่งซื้อถาวร, outbox และ ledger แต้ม: **Not evidenced in the provided files** โค้ดที่อ่านแสดงการสร้าง OrderResult ในหน่วยความจำและคืน response เท่านั้นใน PlaceOrder (system/online-boutique/src/checkoutservice/main.go:265–279) ADR-0001 เป็นการตัดสินใจเรื่อง cart storage จึงไม่ได้ยืนยันว่ามี order store หรือมี durability เพียงพอสำหรับงานนี้ (docs/adr/0001-use-redis-for-cart-storage.md:36–45)

## Decision drivers

1. **ความพร้อมใช้งาน:** การหยุดทำงานของผู้รับงานหลังสั่งซื้อห้ามทำให้คำสั่งซื้อล้มเหลว (docs/scenario.md:28)
2. **ความถูกต้องและความทันเวลา:** ให้แต้มครั้งเดียวต่อคำสั่งซื้อภายใน 1 นาที (docs/scenario.md:27)
3. **ประสิทธิภาพ:** รักษา p95 checkout ≤ 500 ms ที่พีก 200 orders/s และควบคุมอัตราส่ง MailFast (docs/scenario.md:24–26)
4. **ความสามารถในการปรับเปลี่ยน:** เพิ่มงานหลังสั่งซื้อได้โดยลดการแก้ checkout (docs/scenario.md:14; เป้าหมายการลดการแก้ไขเป็น **[Inferred]**)
5. **ต้นทุนและความง่ายในการดูแล:** เหมาะกับทีม 4 คน ทักษะที่มี และ Kubernetes แบบ self-hosted (docs/scenario.md:29–30)

## Considered options

1. ให้ checkout เรียกอีเมล loyalty และ analytics โดยตรงผ่านการเรียกแบบ synchronous พร้อมกำหนด timeout และจัดการข้อผิดพลาด
2. บันทึกงานถาวรแล้วให้ตัวประสานงานเบื้องหลังเรียกบริการต่าง ๆ ผ่าน gRPC โดยติดตามสถานะและ retry แต่ละงาน
3. บันทึกคำสั่งซื้อและ outbox แบบ atomic แล้วกระจายเหตุการณ์ผ่าน RabbitMQ ไปยังคิวแยกของแต่ละงาน

ทั้งสามข้อเป็นทางเลือกที่เสนอใหม่จากข้อกำหนดใน docs/scenario.md:7–30 ไม่ใช่คำอธิบายสถาปัตยกรรมที่มีอยู่แล้ว

### Pros and cons of the options

| ทางเลือก | ข้อดี | ข้อเสีย |
|---|---|---|
| 1. เรียกโดยตรง | โครงสร้างใกล้กับ PlaceOrder ปัจจุบันและใช้ทักษะ gRPC ของทีม (main.go:273–279, 379–383; docs/scenario.md:29) | **[Inferred]** MailFast เพิ่มเวลารอและเสี่ยงเกินเป้า latency; timeout หรือการข้ามข้อผิดพลาดอย่างเดียวไม่ทำให้งานส่งสำเร็จภายหลัง; การเพิ่มงานต้องแก้ checkout (docs/scenario.md:14, 24–28) |
| 2. ตัวประสานงานเบื้องหลัง | **[Inferred]** แยกเวลารอจาก checkout ใช้ Go/gRPC ที่ทีมถนัด และดูสถานะรวมต่อคำสั่งซื้อได้ (docs/scenario.md:24, 29) | **[Inferred]** ต้องสร้างกลไกงานถาวร retry และติดตามสถานะเอง; ตัวประสานงานต้องรู้จักงานใหม่และแยกการจัดสรรทรัพยากรเพื่อไม่ให้ MailFast ที่ช้าขวาง loyalty (docs/scenario.md:14, 26–27) |
| 3. เหตุการณ์ผ่าน RabbitMQ | **[Inferred]** แยกคิวและผู้รับงาน เพิ่มผู้รับงานใหม่ได้โดยไม่เพิ่มการเรียกใน checkout; เหมาะกับประสบการณ์ RabbitMQ ของสมาชิก 2 คนและแนวทาง self-hosted (docs/scenario.md:14, 29–30) | **[Inferred]** เพิ่ม broker และที่เก็บข้อมูลถาวรที่ต้องดูแล; ต้องออกแบบรับข้อความซ้ำ การเปลี่ยน schema และการติดตามงาน; broker เพียงอย่างเดียวไม่รับประกันแต้มครั้งเดียว (ข้อกำหนด docs/scenario.md:27–30) |

## Decision

เลือก **ทางเลือก 3** สำหรับการออกแบบฉบับนี้ เพื่อแยกความล่าช้าและความล้มเหลวของงานหลังสั่งซื้อ และรองรับงานใหม่ตาม R-12 โดยใช้ประสบการณ์ RabbitMQ ของทีม (docs/scenario.md:7–14, 24–30) รายละเอียดต่อไปนี้เป็นการออกแบบที่เสนอใหม่ทั้งหมด:

- **จุดสร้างเหตุการณ์:** หลังชำระเงินและส่งสินค้าสำเร็จ ให้บันทึกคำสั่งซื้อที่ยืนยันแล้วพร้อม outbox ของเหตุการณ์ OrderPlaced ใน transaction เดียว ก่อนตอบ checkout สำเร็จ ตำแหน่งปรับอยู่บริเวณที่สร้าง OrderResult และเรียกอีเมลเดิม (main.go:252–279) เลือกเพิ่ม PostgreSQL สำหรับ order/outbox และ ledger โดยแยกขอบเขตข้อมูลตามบริการ ทั้งหมดเป็นการตัดสินใจออกแบบใหม่ ไม่ใช่เทคโนโลยีที่หลักฐานยืนยันว่ามีอยู่แล้ว; ไม่ถือว่า Redis สำหรับ cart เป็น order store (docs/adr/0001-use-redis-for-cart-storage.md:36–45)
- **การส่งต่อ:** ให้ relay อ่าน outbox แล้วส่งเข้า RabbitMQ ผ่าน AMQP ใช้ข้อความ persistent คิว durable แบบ quorum และ publisher confirms; ทำเครื่องหมายว่าส่งแล้วหลังได้รับ confirm เท่านั้น หากขัดข้องให้ส่งใหม่ได้ นโยบายนี้เสนอเพื่อรองรับความพร้อมใช้งานตาม docs/scenario.md:28, 30 ต้องพิสูจน์ด้วยการทดสอบ ไม่ถือว่าคุณสมบัติ broker ทำให้กระบวนการทั้งหมดเป็น exactly-once
- **การกระจาย:** ใช้ exchange สำหรับ OrderPlaced และคิวแยกสำหรับผู้ส่งอีเมล loyaltyservice และผู้บันทึก analytics ให้แต่ละงานได้รับสำเนาของเหตุการณ์ ไม่ใช้คิวเดียวที่ผู้รับงานทั้งสามแย่งข้อความกัน เพิ่มคิวสำหรับงานใหม่ตาม docs/scenario.md:14 ได้โดยไม่เพิ่มการเรียกบริการใน checkout
- **สัญญาเหตุการณ์:** เสนอให้มี event_id, order_id, เวลายืนยันคำสั่งซื้อ, schema_version และข้อมูลขั้นต่ำที่แต่ละงานต้องใช้ โดยพิจารณา OrderResult, req.UserId และ req.Email ที่มีใน PlaceOrder (main.go:230–279) ห้ามใส่ req.CreditCard ลงเหตุการณ์; อายุเก็บข้อมูลและสิทธิ์เข้าถึงต้องตกลงก่อนใช้งานจริง
- **การรับซ้ำและแต้ม:** ออกแบบการส่งแบบ at-least-once ให้ loyaltyservice บันทึก ledger แต้มและหลักฐานประมวลผลใน transaction เดียว พร้อม unique key ของ order_id กับชนิดการให้แต้ม แล้ว ack หลัง commit การส่งซ้ำต้องคืนผลเดิมโดยไม่เพิ่มแต้มอีก ห้ามแยกการจำว่าเคยรับข้อความกับการเพิ่มแต้มเป็นคนละ transaction ข้อเสนอนี้มุ่งให้ผลทางธุรกิจเกิดครั้งเดียวตาม docs/scenario.md:27 ไม่ใช่รับข้อความครั้งเดียว
- **อีเมลและ analytics:** ปรับ emailservice เป็นผู้รับงานเบื้องหลังที่ส่งผ่าน MailFast แทนการเรียก synchronous จาก checkout ตาม R-12 (docs/scenario.md:10; main.go:273–277, 379–383) จำกัดอัตรารวมทุก replica ไม่เกิน 50 emails/s รวม retry ใช้ backoff และแยก retry queue; การเรียก MailFast ใช้ protocol/API ที่ต้องยืนยันกับผู้ให้บริการ ผู้บันทึก analytics ต้อง deduplicate ด้วย event_id และ ack หลังบันทึกสำเร็จ
- **งานผิดพลาด:** ใช้ manual ack หลังผลลัพธ์ถาวรสำเร็จ แยก retry และ dead-letter queue ต่อประเภทงาน พร้อมแจ้งเตือนและกระบวนการ replay ค่า retry limit และระยะเวลาเก็บยังต้องตกลง การเข้า dead-letter queue ไม่ถือว่าทำ requirement สำเร็จ โดยเฉพาะแต้มที่กำลังจะเกิน 1 นาที (docs/scenario.md:27)

**ขอบเขตการรับประกัน:** checkout ไม่รอ MailFast, loyalty หรือ analytics และเมื่อ RabbitMQ หยุดชั่วคราวให้สะสม outbox ต่อได้ตราบเท่าที่ที่เก็บยังพร้อมและมีพื้นที่ การบันทึกถาวรยังเป็น dependency ใหม่ของ checkout; หากบันทึกไม่ได้ จะยังรับรองทั้งการตอบสำเร็จและการไม่สูญเหตุการณ์ไม่ได้ ให้ใช้พฤติกรรมใน Decision boundaries and failure handling และทดสอบก่อนเปิดใช้ (docs/scenario.md:28; main.go:265–279) นอกจากนี้ payment และ shipping เป็นการเรียกภายนอกก่อนจุดบันทึก จึงยังมีช่องว่างเมื่อ process หยุดหลังเกิดผลข้างเคียง ต้องออกแบบ reconciliation และ idempotency เพิ่ม การมี outbox ไม่ทำให้สองการเรียกนี้อยู่ใน transaction เดียวกัน (main.go:252–261)

### Decision boundaries and failure handling

รายละเอียดต่อไปนี้เป็นข้อกำหนดการออกแบบใหม่เพื่อตอบประเด็นรีวิว ไม่ใช่ผลการทดสอบหรือข้อเท็จจริงเพิ่มเติมจาก scenario

1. **การรับคำขอและสถานะคำสั่งซื้อ:** ให้ client ส่ง idempotency key คงเดิมสำหรับการลองคำขอเดิมซ้ำ บันทึก key, request fingerprint และ order_id แบบ unique พร้อมสถานะเริ่มต้นใน PostgreSQL ก่อนเรียก payment/shipping หาก key เดิมแต่ข้อมูลต่างกันให้ปฏิเสธ; หากข้อมูลเดิมให้คืนสถานะ/ผลเดิมและไม่เริ่มชำระเงินซ้ำ คำขอซ้อนต้องมีผู้ประมวลผลได้เพียงรายเดียว ต้องทดสอบกลไก lock และ recovery
2. **ขอบเขต transaction:** บันทึกความคืบหน้า payment/shipping และรหัสอ้างอิงเพื่อ reconciliation; เมื่อทั้งสองสำเร็จจึง commit สถานะ Confirmed, confirmed_at และ outbox ใน transaction เดียวกัน หาก process หยุดระหว่างผลภายนอกกับการบันทึก ให้คงคำสั่งซื้อในสถานะรอตรวจสอบและห้ามเรียกซ้ำโดยเดา ต้องยืนยันวิธีตรวจผล/idempotency ของบริการก่อนเปิดใช้ ไม่อ้างว่า PostgreSQL ทำให้การเรียก gRPC เป็น transaction เดียวกัน
3. **เมื่อบันทึกไม่ได้:** หากยังไม่ได้เริ่มผลภายนอก ให้ปฏิเสธชั่วคราวและให้ลองด้วย key เดิม หากเริ่ม payment/shipping แล้วแต่ยืนยันผลไม่ได้ ให้รายงานสถานะยังไม่ยืนยันพร้อม order_id เมื่อทำได้; client ต้องตรวจสถานะด้วย key เดิมหลัง timeout ห้ามตอบสำเร็จจน commit Confirmed/outbox แล้ว บันทึกพื้นที่คงเหลือและหยุดรับงานใหม่ก่อนพื้นที่เต็ม; ข้อจำกัดของ store เป็น dependency ใหม่ที่ต้องประเมิน ไม่ซ่อนเป็นความล้มเหลวของ email/loyalty/analytics
4. **เส้นตายแต้ม:** กำหนดจุดเริ่มเป็น confirmed_at ใน transaction ที่ยืนยัน order โดยให้เวลารอ relay, queue, retry และ commit ledger รวม ≤ 60 วินาที ห้ามเลื่อนเวลาเริ่มเมื่อ replay และห้ามลด requirement ให้เหลือเพียง eventual completion การหยุด loyalty จนเกิน deadline ต้องบันทึกเป็นการผิดข้อกำหนดและแจ้งเตือนทันที; ต้องให้เจ้าของข้อกำหนดยอมรับแผนความพร้อมใช้งานก่อนเปิดใช้ ไม่มีการสมมติว่า outage ได้รับยกเว้น
5. **ความจุอีเมล:** ภายใต้หนึ่งอีเมลต่อ order และส่งได้เต็ม 50/s พีก T วินาทีทำให้ค้างอย่างน้อย 150T ฉบับก่อน retry; หลังพีก หากโหลดใหม่เป็น r orders/s และ r < 50 เวลาระบายอย่างดีที่สุดคือ backlog/(50-r) วินาทีโดยยังไม่รวม retry เป็น [Inferred] จาก docs/scenario.md:25–26 หาก r ≥ 50 จะระบายไม่หมด ต้องยืนยัน T, r, เส้นตายอีเมล และขนาดข้อความเพื่อกำหนดพื้นที่/retention หรือเพิ่มโควตาก่อนเปิดใช้ โดยจำกัดอัตรารวมทุก replica
6. **งานใหม่และความเป็นเจ้าของ:** เพิ่ม SMS/recommendations เป็นผู้รับเหตุการณ์เมื่อข้อมูลเพียงพอ; fraud scoring ที่ใช้อนุมัติคำสั่งซื้อต้องตัดสินก่อน Confirmed และอยู่นอกการแยกงานหลังสั่งซื้อครั้งนี้ จนกว่าจะยืนยันความหมายทางธุรกิจ ในแบบฝึกหัด ชินนวุฒิ แก้วฉิมรับผิดชอบติดตามประเด็นค้าง ส่วนระบบจริงต้องมีผู้รับผิดชอบ broker/store, แต่ละ consumer และเวรตอบสนองเหตุขัดข้องก่อนเปิดใช้

**เหตุผลที่เลือกแทนทางเลือก 2:** ทั้งสองทางแยก latency ของ MailFast ได้ แต่ R-12 ระบุว่าจะเพิ่มผู้รับงานหลายประเภท จึงเลือกกระจายเหตุการณ์และแยกคิวตามงาน ยอมรับภาระ broker เพิ่ม โดยทักษะ RabbitMQ ของสมาชิก 2 คนช่วยลดความเสี่ยงในการเริ่มต้น ไม่ใช่หลักฐานว่าใช้ทรัพยากรน้อยกว่าตัวประสานงาน ต้องเปรียบเทียบจำนวนจุดแก้ไขเมื่อเพิ่มผู้รับงาน การแยกคิวเมื่อ MailFast ช้า และภาระดูแลจริงในต้นแบบ (docs/scenario.md:14, 29–30; [Inferred])

## Consequences

- **Positive:** checkout ไม่ต้องรอ MailFast ที่มี p95 1.5 s และความล้มเหลวของผู้รับงานถูกแยกด้วยคิว; ต้องวัดผลจริงว่า checkout ยังผ่าน 500 ms หลังเพิ่มการบันทึกถาวร (คุณลักษณะ: ประสิทธิภาพ, ความพร้อมใช้งาน; docs/scenario.md:24–28)
- **Positive:** เพิ่มผู้รับงานหลังสั่งซื้อได้ผ่านคิวและสัญญาเหตุการณ์ ส่วน ledger ป้องกันแต้มซ้ำจากการส่งซ้ำ (คุณลักษณะ: ความสามารถในการปรับเปลี่ยน, ความถูกต้อง; docs/scenario.md:14, 27; เป็นผลที่คาดหวังของข้อเสนอ)
- **Negative:** ต้องดูแล broker ที่เก็บคำสั่งซื้อ/outbox และ ledger รวมถึง backup, recovery และ schema; เพิ่มภาระทีม 4 คนและต้นทุนทรัพยากร (คุณลักษณะ: ความสามารถในการดูแล, ต้นทุน; docs/scenario.md:29–30; **[Inferred]**)
- **Negative:** งานหลังสั่งซื้อเสร็จภายหลัง response สำเร็จ จึงต้องแสดงและติดตามสถานะค้าง ไม่อ้างว่าทุกงานเสร็จทันที (คุณลักษณะ: ความสอดคล้องของข้อมูล, ความสามารถในการสังเกตการณ์; ข้อเสนอจาก docs/scenario.md:24–28)
- **Risks and mitigations:** หากทุกคำสั่งซื้อมีอีเมลหนึ่งฉบับ ที่พีก 200 orders/s เทียบกับขีดจำกัด 50 emails/s จะสะสมอย่างน้อย 150 ฉบับ/วินาที ก่อนนับ retry เป็น **[Inferred]** จาก docs/scenario.md:25–26 คิวช่วยพักงานแต่ไม่เพิ่มขีดจำกัด MailFast ต้องตกลงเวลาส่งอีเมลและระยะพีก หรือเพิ่มโควตา; แยกคิวแต้มเพื่อไม่ให้รอคิวอีเมล (คุณลักษณะ: scalability, ความทันเวลา)
- **Risks and mitigations:** หาก loyalty หรือโครงสร้างพื้นฐานหยุดเกิน 1 นาที จะไม่สามารถรับรอง deadline เดิมทุกคำสั่งซื้อได้ แม้ไม่ทำให้คำสั่งซื้อล้มเหลว ต้องตกลงขอบเขต SLA และวิธีกู้คืน ติดตามอายุข้อความตั้งแต่ยืนยันคำสั่งซื้อพร้อมแจ้งเตือนก่อนเกินกำหนด (คุณลักษณะ: ความพร้อมใช้งาน, ความทันเวลา; docs/scenario.md:27–28)
- **Risks and mitigations:** การส่ง MailFast สำเร็จแล้วขาดการตอบกลับอาจทำให้อีเมลซ้ำเมื่อ retry ต้องยืนยันว่าผู้ให้บริการรองรับ idempotency key หรือการตรวจสอบผลก่อนกำหนดการรับประกันการส่ง (คุณลักษณะ: ความถูกต้อง; เป็นความเสี่ยงของข้อเสนอที่ใช้บริการภายนอกตาม docs/scenario.md:10, 26)

## Validation

- ทดสอบครบเส้นทางที่ 200 orders/s รวมการบันทึกคำสั่งซื้อ/outbox และ relay; PlaceOrder ต้องมี p95 ≤ 500 ms วัด latency ตั้งแต่ยืนยันคำสั่งซื้อถึงเพิ่มแต้มและตรวจว่าแต่ละคำสั่งซื้อได้รับแต้มครั้งเดียวภายใน 60 วินาทีโดยนับจาก confirmed_at และไม่ยกเว้น outage เอง (docs/scenario.md:24–27) ระยะเวลาทดสอบพีกยังต้องขอข้อมูล
- จำลอง MailFast ตาม p95 1.5 s, p99 8 s, อัตราผิดพลาดประมาณ 0.5% และขีดจำกัด 50 emails/s ตรวจว่าอัตรารวมพร้อม retry ไม่เกินโควตา คิวแต้มไม่ถูกงานอีเมลขวาง และวัด backlog กับเวลากลับสู่ปกติ (docs/scenario.md:26–27)
- ปิดผู้รับงานอีเมล loyalty และ analytics แยกกัน ตรวจว่า checkout ยังสำเร็จ เหตุการณ์ยังอยู่ และหลังกลับมางานถูกประมวลผลครบ บันทึกกรณีแต้มเกิน 60 วินาทีเป็นการผิดข้อกำหนด ไม่ถือว่า eventual recovery ทดแทน deadline ได้ (docs/scenario.md:27–28)
- จำลอง process หยุดหลัง commit outbox, หลัง publish ก่อนทำเครื่องหมายส่งแล้ว และหลัง commit ledger ก่อน ack ตรวจว่าไม่มีเหตุการณ์ของคำสั่งซื้อที่ยืนยันแล้วสูญหาย ไม่มีแต้มซ้ำ และ analytics ไม่ถูกนับซ้ำ ตรวจ reconciliation ของกรณีหยุดหลัง payment/shipping ด้วย (จุดเสี่ยง main.go:252–279; กลไกป้องกันเป็นข้อเสนอใน ADR นี้)
- ทดลองหยุด broker และที่เก็บข้อมูลแยกกัน ตรวจ replay, publisher confirms, พื้นที่ค้างและนโยบายเมื่อเขียนไม่ได้ รวมถึงทดสอบ backup/restore ทบทวนผลก่อนเปลี่ยนสถานะ ADR เป็น Accepted; ทบทวนก่อนเปิดใช้สำหรับ 11.11 และทุกครั้งที่ผลทดสอบไม่ผ่าน โดยไม่อ้างว่าทดสอบแล้ว

### Release gates

- ห้ามเปิดใช้จริงจนมีผลทดสอบ latency, แต้มครั้งเดียวภายใน 60 วินาที, outage, crash recovery และ backup/restore ครบตามรายการด้านบน การกู้คืนสำเร็จภายหลังไม่ลบการละเมิด deadline
- ต้องยืนยันระยะพีก โหลดหลังพีก เส้นตายอีเมล โควตา และพื้นที่ outbox/queue พร้อมระบุผู้รับผิดชอบและ runbook ก่อนเปิดใช้ ไม่สร้างค่าทดแทนข้อมูลที่ scenario ไม่ให้
- หากต้องหยุดการเปิดใช้ ให้หยุดรับคำสั่งซื้อใหม่ตามกระบวนการปฏิบัติการและรักษา outbox/ledger/ข้อความค้างเพื่อกู้คืน ห้ามลบคิวหรือเริ่มส่งซ้ำโดยข้าม deduplication; ห้ามสลับกลับไปเรียก MailFast แบบ synchronous โดยไม่มีผลทดสอบรองรับ
- สถานะเอกสารคง Proposed ตามมติจำลองที่มีเงื่อนไข เปลี่ยนเป็น Accepted เมื่อผู้รับผิดชอบทบทวนหลักฐานและปิดเงื่อนไข ไม่ถือว่าการส่งเอกสารหรือการเขียนแผนทดสอบเป็นการผ่านเกณฑ์
